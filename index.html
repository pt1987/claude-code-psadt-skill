The SYSTEM test costs the host nothing

Five deployment actions, each followed by a detection evaluation — ten recorded steps, run as NT AUTHORITY\SYSTEM inside a throwaway Windows Sandbox VM against a machine that has never seen the app.

  1. 1 Install → detect
  2. 2 Uninstall → detect
  3. 3 Reinstall → detect
  4. 4 Repair → detect
  5. 5 Uninstall → detect

The run itself needs no elevation and leaves the host untouched. Enabling the Sandbox feature is a one-time elevated step, and it needs Windows Pro, Enterprise or Education with virtualisation available.

A vendor-signed kernel driver is RED, not a warning.

Classified before anything is built, because the alternative is a package that installs cleanly and then fails to load on every device.

GREEN

Microsoft-signed (WHQL, Attestation or inbox)

Pre-stage with pnputil, then run the installer. No certificate work.

WARN

Vendor-signed, user-mode

The signer certificate becomes a deliverable — preferably an Intune policy, not a package import. Own it in exactly one place.

RED

Vendor-signed kernel-mode, with Secure Boot on

Refused. TrustedPublisher removes the PnP prompt but never satisfies Code Integrity, so the driver would install and then fail to load. There is no packaging trick. An explicit opt-out exists for fleets that genuinely run Secure Boot off.

Pre-flight that names the file

Ten check categories — encoding and BOM, AST parse, launcher acid test, a scan for v3 cmdlets, hook structure, the detection contract, the manifest, the per-run log name, driver trust. The verdict is GREEN or RED, and RED tells you which file.

Four questions, not forty

Scope, deployment semantics, SYSTEM-test consent, upload confirmation. Everything else — the current version, the silent switches, the ProductCode, known Intune issues — is researched and stated as an assumption.

4 decision gates

One manifest, one truth

psadt-package.json holds the identity, the decisions taken at the gates, the research findings, every phase result and every artifact. Generators write it, later phases read it, pre-flight fails without it — which is what stops two packages of the same app from disagreeing about their own version.

<pkg>\psadt-package.json

All three deployment types, from the start

Install, Uninstall and Repair are filled and acid-tested together, even when only install is needed today — because a Company Portal uninstall needs a real Uninstall hook, not a placeholder.

Install · Uninstall · Repair

A vendor-signed kernel driver is RED, not a warning

Drivers are classified before anything is built. With Secure Boot on — the default on Windows 11 — the kernel loads only Microsoft-signed drivers: TrustedPublisher removes the PnP prompt but never satisfies Code Integrity, so the driver would install and then fail to load. There is an explicit opt-out for fleets that genuinely run Secure Boot off.

The dossier is not optional

Every package gets one self-contained Intune-Dossier.html — app info, a paste-ready Markdown Company Portal description, the return-code map, the detection rule, driver trust, plus the technical report with pre-flight and SYSTEM-test results. Bilingual, no external requests.

New-PsadtReport.ps1

Upload that refuses to be destructive

A raw Graph win32LobApp push with no third-party module: dry run, then confirm, then upload. It fills every objective app-info field, never imposes a category, and by default never deletes an older version — new versions coexist so you wire supersedence yourself. Replacing an app in place is a separate, explicit flag.

Invoke-IntuneWin32Upload.ps1

Access as state, not as a 403

Before any upload or policy write, the skill reads its own capabilities and reports them three-valued — granted, missing, or genuinely unknown — and offers the exact fix. It does not probe a tenant by provoking an error.

Updates without losing your setup

Self-update pulls from GitHub and touches tracked files only. config.json, the DPAPI secret and the downloaded tools live in %LOCALAPPDATA%\psadt-deploy, so they survive an update, a re-clone and a re-install.

Fourteen installer engines, and the trap in each

Identified by fingerprint, not by guesswork, and consulted before any web search. Two of them — MSIX and App-V — are routed away from PSADT rather than wrapped in it.

MSI

silent msiexec /i pkg.msi /qn

detect ProductCode

MSI-wrapped EXE

silent setup.exe /s /v"/qn /norestart"

detect ProductCode

Extract the MSI and probe it rather than trusting the wrapper.

InstallShield (Basic MSI)

silent setup.exe /s /v"/qn"

detect ProductCode

InstallShield (InstallScript)

silent setup.exe /s /f1"setup.iss"

detect registry / file

Record the response file first with setup.exe /r /f1"setup.iss".

Inno Setup

silent setup.exe /VERYSILENT /NORESTART

detect QuietUninstallString

/VERYSILENT reboots the machine by itself when a restart is needed. /NORESTART is mandatory.

NSIS

silent setup.exe /S

detect registry / file

Uninstall.exe /S returns BEFORE it is done. _?=<installdir> makes it synchronous.

Advanced Installer

silent msiexec /i pkg.msi /qn

detect ProductCode

A fresh ProductCode per build is typical — re-probe every time.

WiX Burn bundle

silent bundle.exe /quiet /norestart

detect BundleProviderKey

A single ProductCode is the wrong detection key for a bundle.

Squirrel (Electron)

silent Setup.exe --silent

detect file version under %LocalAppData%

Usually per-user; a machine-wide Win32 install needs care.

MSIX / AppX

silent Add-AppxProvisionedPackage -Online

detect Get-AppxProvisionedPackage

As SYSTEM, Add-AppxPackage registers the app for SYSTEM only — and reports success.

App-V

silent Publish-AppvClientPackage -Global

detect Get-AppvClientPackage

Add alone publishes to nobody. Without -Global a SYSTEM publish targets SYSTEM.

install4j (Java)

silent installer.exe -q

detect registry / file version

NOT /S — that opens the language dialog and hangs forever.

IzPack (Java)

silent installer.jar auto-install.xml

detect registry / file

Response-file driven.

InstallAware / Wise

silent /s or /silent

detect registry / file

Confirm per build — often an MSI underneath.

What this page is not claiming

Figures are as of v0.26.7

Every number on this page was verified against the repository at that version. Counts drift; the linked source is authoritative, not this page.

The timings are single runs

Not benchmarks. One machine, one app, one run each — and the end-to-end figure includes model thinking time, which depends on the model and the network.

Windows Sandbox has prerequisites

Windows Pro, Enterprise or Education with virtualisation available. Enabling the Containers-DisposableClientVM feature needs elevation and one restart — after that, a test run needs neither.

Upload is opt-in, and non-destructive by default

The default keeps older versions side by side so you can wire supersedence yourself. Replacing an app in place is a separate, explicit flag.

Not affiliated

Not affiliated with or endorsed by Microsoft. PSAppDeployToolkit is a separate MIT-licensed project by its own authors; this skill drives it, it does not replace it.

One open point, stated plainly

The driver pnputil exit-code semantics are documented, not verified here. 0 / 259 / 3010 and the two 0xE… failures come from Microsoft’s documentation; confirming them against setupapi.dev.log on a DEV VM with a real vendor-signed and a real Microsoft-signed driver is still open.
